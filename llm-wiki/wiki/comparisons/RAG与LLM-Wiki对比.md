# RAG 与 LLM Wiki 对比

## 对比目的

帮助读者理解 RAG 和 LLM Wiki 两种知识管理方案的差异，在不同场景下做出合适选择。

## 对比总览

| 维度 | RAG | LLM Wiki |
|------|-----|----------|
| 核心理念 | 实时检索 + 增强生成 | 预先编译 + 结构化页面 |
| 知识处理 | 分块 → 向量化 → 检索 | 理解 → 提炼 → 编写 |
| 知识形态 | 文本片段（chunks） | 完整结构化页面 |
| 上下文完整性 | 容易断裂 | 页面内完整 |
| 维护者 | 自动索引 | AI Agent + 人类 |
| 更新方式 | 重新分块和索引 | Agent 增量修改页面 |
| 链接关系 | 无 | [[双向链接]] |
| 可读性 | 低（碎片） | 高（完整页面） |
| 可审计性 | 低 | 高（Git diff） |
| 虚构/幻觉风险 | 中高 | 低 |
| 初始成本 | 低（自动索引） | 高（需要 AI Agent 编译） |
| 推理能力 | 依赖检索质量 | 页面内已包含推理结果 |
| 适用资料量 | 海量非结构化文档 | 需要深度理解的核心知识 |
| 典型工具 | LangChain, LlamaIndex, Pinecone | Git + Markdown + AI Agent |
| 适合场景 | 客服、法律文档搜索、内部知识库问答 | 个人知识库、研究沉淀、项目文档 |

## 详细对比

### 知识质量

- **RAG**：质量取决于分块策略。块太大 → 噪声多；块太小 → 上下文断裂。检索也可能返回不相关内容。
- **LLM Wiki**：AI Agent 事先理解、消化、提炼，页面质量经过"编辑"过程，更可靠。

### 上下文保持

- **RAG**：查询时从不同 chunk 拼接上下文，不同 chunk 之间没有关联。
- **LLM Wiki**：每个页面是完整独立的上下文单元，页面间通过 [[双向链接]] 关联。

### 维护性

- **RAG**：文档更新后需要重新分块、重新 embedding、重新索引。难以做增量更新。
- **LLM Wiki**：Agent 直接修改对应页面，Git 追踪变更，可增量更新。

### 虚构问题

- **RAG**：LLM 可能被不相关的检索结果误导，或者在拼接的碎片中"脑补"不存在的信息。
- **LLM Wiki**：每个页面有明确的 sources，AI 被约束在已有知识范围内回答，虚构风险更低。

### 适用场景互补

并不是非此即彼：

- **RAG 更适合**：海量文档（数万篇）、快速变化的文档、简单事实查询
- **LLM Wiki 更适合**：需要深度理解的知识、需要交叉引用的体系、长期维护的知识库
- **可以组合**：RAG 做初筛，LLM Wiki 做深度回答；或 LLM Wiki 作为 RAG 的"精选知识层"

## 结论与建议

- 如果你有大量非结构化文档且需要快速检索 → 用 RAG
- 如果你需要深度理解、长期维护的知识体系 → 用 LLM Wiki
- 两者不互斥，可以根据场景灵活组合
